The backend suite includes real Postgres/Redis behavior; calling all of it “unit tests” obscures what it verifies. The testing guide's claim that the complete suite stays under 30 seconds is stale (`docs/internal/testing/README.md:30`).

Two recent failed backend runs ([38948105096](https://github.com/zzstoatzz/plyr.fm/actions/runs/38948105096), [38947910074](https://github.com/zzstoatzz/plyr.fm/actions/runs/38947910074)) failed in the separate live private-media step: `httpx.ReadTimeout` while creating the PDS app-password session. These are external-boundary failures, not evidence that the local test suite needs more workers. Keep the live check: it covers a boundary the local suite cannot.

The first clean local invocation selected Python 3.14.7 and 18 workers automatically, then stalled near completion without a summary. It was interrupted and its services removed before the Python 3.12/four-worker run. This does not isolate Python version from worker count or machine load; do not attribute the stall to one of them. A local interpreter pin matching the deployed Python 3.12 would remove one source of variation.

The completed local run's slowest calls were the queue pressure test (7.91s), two PDS retry-exhaustion tests (7.01s each), a fresh-interpreter import test (3.97s), and the database health timeout test (3.05s). The PDS tests deliberately pay real 1s+2s+4s backoffs (`backend/tests/test_pds_network_retry.py:82-106` and the corresponding upload test). A focused speed improvement could use a shorter configured backoff while still executing the real retry loop and checking failure/recovery behavior. This saves test work; it is not a promised 14-second wall-time improvement under xdist.

The queue pressure test passed when rerun alone with the same Python version and four workers (2.29s call, 7.04s pytest total). In the full run, its assertion at `backend/tests/test_queue.py:201` rejected a warning from `_listen_loop`; this test explicitly starts only `_heartbeat_loop`. A session-scoped TestClient elsewhere starts the singleton queue listener (`backend/tests/conftest.py:564-587`). This points toward background-service/test isolation as a follow-up, but the emitting instance was not instrumented, so the precise cause is unconfirmed. Do not suppress the warning or simply increase the timeout. The failed full run also confirmed that the recipe leaves its Compose services running; the successful focused rerun removed them.

The local 25 skips comprise 22 token-dependent tests in `tests/integration`, one live ZDS test, and two legacy upload tests. Their separate CI workflows matter; “25 skipped” alone is not a coverage-loss diagnosis. SQLAlchemy also reported pooled connections being garbage-collected without return to the pool. The warning location identifies where collection happened, not necessarily where the connection leaked.

## Cleanup PR boundaries

### 1. Make CI dependency checks reliable and timings visible

- `.github/workflows/run-pre-commit.yml:49` hashes the absent `frontend/bun.lockb`; the repository uses `frontend/bun.lock`. Fix the cache key.
- The same workflow runs unlocked `uv sync` at line 56 before `uv lock --check` at line 71. Sync can update the lockfile before the validation sees it. Use `uv sync --locked` and remove the redundant later check. Backend tests already use locked sync.
- Add `--durations=20 -rs` to the existing backend pytest invocation. Passing CI currently hides which tests are slow and why 25 tests skip. Preserve the separate required live private-media check.
- Expose the frontend test summary through the existing hook's verbose output or a named CI step. The prek trace gives hook timing, but normal passing output hides test counts. Do not run the suite twice to obtain a summary.

Validation: a deliberately stale lockfile must fail before being rewritten; a lockfile change must produce a different cache key; passing logs should show counts, skips, and durations. No extra matrix needed.

### 2. Align image inputs, workflow triggers, and release eligibility

- `backend/Dockerfile:19` copies `lexicons/`, but lexicon-only changes trigger neither `.github/workflows/build-docker.yml:4-11` nor `.github/workflows/deploy-staging.yml:7-15`.
- Image validation also omits `backend/alembic/**` and `backend/alembic.ini`, which the Dockerfile copies. Staging deployment already includes those migration paths.
- `scripts/release:56-70` recognizes source, migrations, and cost scripts, but excludes dependency-only, Dockerfile-only, and lexicon-only changes. These can change the deployed backend image while the release helper refuses them as “no backend changes.”

Validation: enumerate actual image inputs and check representative changed-file sets against both PR validation and staging/release eligibility. Keep this an explicit list; a new generic workflow framework would add more than it removes.

### 3. Repair the contributor path and test recipes

- `docs/internal/local-development/setup.md:20` runs `uv sync` from the repository root, where there is no Python project. Later Python commands repeat the missing backend context. The public contributing guide uses the correct directory.
- Internal setup lines 60 and 333–334 send OAuth back to frontend port 5173. `backend/.env.example:42` uses port 8000. The backend recipe serves port 8001, and `/auth/callback` is a backend route (`backend/src/backend/api/auth.py:203`). Align the example and guide with the actual local endpoint; retain the separate guidance about externally reachable OAuth metadata.
- Internal setup line 167 says `cd transcoder`, but the directory is `services/transcoder`. Its `/backend/background-tasks/` and `/deployment/environments/` links are neither valid public-doc routes nor repository-relative links.
- `backend/justfile:39-41` sources a root `.env` and runs the legacy single-token upload test. Current integration documentation describes `backend/tests/integration`, with three test tokens. Name the legacy command explicitly or replace it with the documented suite and clear environment requirements. Do not silently turn the ordinary local test command into a live staging mutation.
- `backend/justfile:24-37` reaches `compose down` only if pytest succeeds. Both parallel and serial recipes should preserve pytest's exit status while cleaning up on failure/interruption.
- Replace the duplicated quickstart in the internal guide with a link to the public contributor guide, retaining only additional local-development details. Update the testing guide to use the existing `test-serial` recipe for debugging and remove the unmeasured “under 30 seconds” promise.

Validation: follow the public guide from a clean directory; check recipe names; exercise a failing local test and confirm only its own Compose project is removed. The existing per-checkout Compose project name and port overrides are good and should stay.

### 4. Make Storybook represent the app, then test both themes

Browser inspection of [TrackItem](https://plyr-storybook.pages.dev/?path=/story/track-trackitem--default) showed light-theme tags failing axe color contrast at **1.71:1** (expected 4.5:1): `#8ab3ff` text on `#e0e8f7`. Dark and light stories were visually inspected.

This is a verified **Storybook discrepancy**, not proof of the same defect in the app: `frontend/src/routes/+layout.svelte:707-710` supplies a light-theme `.tag-badge` override that `frontend/.storybook/plyr-tokens.css` omits. The copied stylesheet also omits the app's track background/border tokens, so previews use component fallbacks.

`frontend/.storybook/preview.ts:10` defaults to dark; `frontend/vitest.storybook.config.ts:36` runs one Chromium instance with no theme matrix. The toolbar makes light mode manually available but does not test it in CI. No screenshot comparison gate was found.

Share the actual theme styles between app and preview, then run the existing axe gate in both themes. Add narrow viewport coverage where layout changes, rather than multiplying every unit test by every browser. Keep manual visual review: axe does not validate spacing, clipping, or resemblance to the app.

Validation: inspect TrackItem in both themes and at narrow/desktop widths, verify computed styles match the app, and run the accessibility suite. Do not hide the discrepancy with a Storybook-only color patch.

### 5. Repair Redis deployment separately

`.github/workflows/deploy-redis.yml:24-25,40-41` uses `working-directory: infrastructure/redis` while passing config paths beginning with `infrastructure/redis/` again. Use paths relative to the working directory. This remains the known failure documented in STATUS.md; the latest two Redis workflow runs failed.

Merging a change to this workflow triggers deployment of staging and then production Redis. Keep it separate from routine lint/test cleanup so that deployment is deliberate.
